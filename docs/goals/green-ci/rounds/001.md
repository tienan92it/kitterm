## Effects

- behaviour: two commits, one per race, each with its reproduction in the
  message.
- **The paced-input race, and a wrong first fix the widening caught.**
  The test typed 8 KiB once `!session.foregroundIsShell` held. `stty` is
  itself a program, so that gate opens while the terminal is still
  cooked; the route then refuses the body with 409 naming `stty`, which
  is what CI recorded. The first fix waited for the reader by name,
  `sleep` or `cat`. The widening (a `sleep 5` before `stty`) then failed
  that fix too, because a cooked `sleep` holds the terminal and satisfies
  the name gate. The committed fix waits on the condition the route
  itself checks, `session.inputIsCanonical == false`. Measured: widened
  plus the old gate failed every run with
  `{"reason":"cooked","foregroundProgram":"sleep"}`; widened plus the new
  gate passed; the real line passes.
- **The takeover race.** The test raced two `POST /api/upgrade/takeover`
  requests and asserted the statuses sorted to `[200, 409]`. Two requests
  started together are not two requests in flight together. The refusal
  is a decision `TakeoverController.admit` makes, so the test now calls
  `admit` three times on one controller and asserts accepted, then
  `.inProgress`, then `.inProgress`, with no timing. The accepted path
  stays covered end to end by
  `testExecTakeoverKeepsPidSessionStreamAndEpoch`, and the route's
  mapping of `.inProgress` to 409 is a `switch` in `serveTakeover`.
- persistent: two test files changed, `Sources/` untouched.
  `swift test --filter 'PacedInputTests|LiveTakeoverTests'` twenty times
  in a row: 20 passed, 0 failed.

## Gap

class: harness
evidence: two failures of the loop, both the foreman's own.

1. The round's first instruction told the crew to reproduce the races
   under an eight-core load. The load starved the daemon, its launchd
   `KeepAlive` agent restarted it, and the crew died with its work. The
   second crew died the same way. The machine's swap was 7.66 GB of
   8 GB used, with a docker VM the largest consumer, so a Swift build
   spike was enough for the kernel to kill a small background daemon
   silently, with no crash report. The method is now deterministic
   widening, which also proved a wrong fix wrong; the load method would
   not have.
2. Cleaning up that load, the foreman matched processes on the bare
   string `yes`, which also matched `ssh -F` command lines and killed two
   of the human's `fly ssh console` connections.

Both are in `facts.md` under Foreman.

## Reflection

The deterministic widening earned its place twice: it reproduced the CI
failure exactly, and it rejected a fix that looked right and was still a
proxy. A load test would have accepted that fix, because under load the
name gate usually opens late enough. The rule is now in the plan: prove
the mechanism, do not make it more likely.
