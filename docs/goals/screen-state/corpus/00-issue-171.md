# Issue #171, as filed

The issue body, copied 2026-10-07 from https://github.com/tienan92it/kitterm/issues/171.

## Context

The foreman must know what a crew pane shows before it types into it: an empty prompt, a running turn, a crew that waits on its own background job, a trust dialog, a permission dialog, or a `claude` that has exited. Today it calls `read_screen` and reads the lines itself. On 2026-09-28 about a dozen `needs-input` events only meant "the crew waits on its own build" (the Claude Code `Notification` hook fires when the agent is idle), and each one cost the foreman a screen read.

We looked at TypeSafe AI's Jev, a hosted model that returns typed decisions with a confidence, and rejected it. Screen text would leave the machine, the pane content is untrusted input that can steer the model, the product is two weeks old, and the markers below are fixed text that plain rules can read.

## Proposal

A tool in the MCP bridge (for example `screen_state`, or a field on `read_screen`) that returns one state and the rule that matched:

| State | Marker (Claude Code 2.1.283) |
|---|---|
| `prompt-empty` | `❯` on the cursor row, box empty or a `{dim}` placeholder only |
| `prompt-has-text` | `❯` on the cursor row with typed text |
| `working` | a spinner line with `esc to interrupt`, or a `⏺` tool call that has not returned |
| `waiting-on-own-job` | `N shell still running` with no question at the prompt |
| `trust-dialog` | `Yes, I trust this folder` |
| `permission-dialog` | `Do you want to proceed` or a numbered Yes/No choice |
| `agent-exited` | a shell prompt and no `claude` in `foregroundProgram` |
| `unknown` | no rule matched: the foreman reads the screen as today |

- It lives in the bridge, beside `KittermScreen` (ADR 0001), so the daemon still judges nothing.
- It makes no network call and has no model or price.
- It reports no invented probability: a matched rule, or `unknown`.

## Plan (a goal: it adds an MCP tool, which is a contract)

1. Record real screens as fixtures under `Tests/`. Drive `claude` in a scratch pane into each state and save each rendered screen. No product change.
2. Build the rules and the tool. Every fixture gives its state, and a screen with no marker gives `unknown`.
3. The foreman skill's "Read before you type" calls the tool first and reads the screen on `unknown`.

## Open questions

- Filtering push notifications by the screen state would be a judgment inside the daemon (`PushNotifier`), which goes against "the daemon never judges". Keep it out of this goal, or decide it separately.
- A Claude Code update can move a marker. The fixture tests catch that; how often do we refresh the fixtures?
