# kitterm product shape

This file holds the section `AGENTS.md` carried until 2026-11-10 (goal `lean-context`), moved here unchanged. A round that changes this surface updates this file.

## Product shape

- **Browser terminal only** — xterm.js client served by a Swift loopback daemon
- Tab open = new shell; session id in `sessionStorage` keeps "tab = shell"
- Transient disconnects (sleep/wake, reload) **detach** the PTY: every output byte flows through a per-session **4MiB ring with absolute stream offsets** (`SessionLog`) — detached reads never pause, the ring rotates. The client counts received bytes and reconnects with `?since=<offset>`; the daemon replays exactly the gap (or the full ring + a resync flag when the offset rotated out, announced via the `logState` frame). **An offset belongs to the stream it was counted on**: when the session the client names is gone (a daemon restart, the reaper) and the daemon spawns a shell in its place, the handler ignores `since`, replays the new shell from its first byte and sets the resync flag (`WebSocketSessionHandler.resolveReplay`), because a stale offset at or below the new shell's byte count is not pruned and its slice landed on the old screen. Client auto-reconnects with backoff + on focus/online/visible; unreattached sessions are reaped after 5 min (suspending clock)
- **Sessions are URLs**: `/?cwd=<path>` deep-links a new shell (`kitterm open <path>`; `kitterm edit <path>` opens `/edit` the same way); `/?session=<uuid>` joins a session — first client is controller, later ones are read-only observers (128KB replay tail, resize broadcast, share button copies the link); `/?hist=<key>` selects a per-pane history file. Observers get a "Take control" overlay (client opcode 5) — live handoff, no reconnect; the demoted side flashes "Another device took control" and keeps watching
- **Session profiles** (`SessionProfiles.swift`): `~/.kitterm/profiles.json` names connect commands (`ssh vm`, `docker exec …`). `/?profile=<name>` spawns a login shell and injects `command\n` as type-ahead input (pre-reader `PtySession.write`, flushed at adoption) — visible, echoed, in the pane's history; if the transport exits you land back in the local shell. The URL carries only the *name*; the command comes only from the file. Reattach ignores the param; a respawn after daemon restart re-runs it. Splits and ⌘⌥T inherit the profile. The fleet view starts no shell (round 11 of `agent-dashboard`) and reads `GET /api/profiles` only to learn whether its token is watch-only; unknown names close 1008 with the reason. In-band OSC (133 marks, 9/777 notifications, OSC 7 cwd) flows through any transport, so remote shells stay fully legible — `kitterm integrate | ssh vm 'cat >> ~/.zshrc'` installs the snippet remotely
- **Fleet view** (`/sessions`: `Web/terminal/src/sessions.ts` paints what the pure, tested `sessions-model.ts`, `sessions-value.ts`, `sessions-tree.ts` and `sessions-stage.ts` decide — `levels`, `goalBuckets`, `band`, `attention`, `rowLine`, `taskLines`, `quotaPanel`, `usagePanel`, `usageHead`, `valuePanel`, `wherePanel`, `modelsPanel`, `leakLines`, `tree`, `visibleLines`, `joins`, `goalStage`, `taskStage`, `reviewLine`; the design of the band and the panels is the two frames `Dashboard 1200` and `Dashboard 390` of `design/dashboard.pen` (the single source of truth; the foreman exports a frame to a scratch directory when a crew needs it), with its `Components` frame for the quota bar, `WHERE` at each filter and the row marks, and the design of the SESSIONS section is the three frames `Sessions 1200`, `Sessions 390` and `Sessions components` of `design/sessions.pen` with the three rules of `docs/goals/sessions-workflow/corpus/01-approved-design.md`, all on the contract in `design/foundation.md`, all frozen). - **Split panes** (client): one browser tab holds a binary tree of panes (⌘D / ⌘⇧D split, ⌘⌥↑↓ / click focus, ⌘⌥T new browser tab in the focused pane's cwd). Layout + per-pane `{sessionId, cwd, histKey}` persist in `sessionStorage`; a reload restores the tree and reattaches each pane. Daemon is unchanged — N panes are just N WebSockets
- **The terminal stack** (`code-editor` round 1, client only): kitterm runs no editor of its own; an editor and lazygit run in panes, and four client additions make them work from a browser and a phone. **OSC 52, write only** (`osc52.ts`, a handler on xterm's own OSC parser, no addon): a program's copy (micro, lazygit, tmux) lands on the viewing device's clipboard through `clipboard.ts`; a read (`?`) is refused and answered with nothing (the handler returns true, so xterm answers nothing either), a payload over 1 MiB decoded is refused whole, replayed bytes copy nothing, and a write the browser refuses (no focus, a plain-HTTP origin, Safari's user-activation rule for every write) keeps the text on a bar on the pane, `Copied from the terminal — tap to copy`, whose one button writes inside the tap. **Touch wheel reports** (`touch-scroll.ts`): a finger drag in a program with mouse reporting on sends one wheel report per row at the finger's cell, SGR when the program set 1006 (the pane tracks `CSI ? 1006 h/l` through a CSI handler, since `Terminal.modes` says whether the mouse is reported, not how), else the X10 form; the normal screen keeps the scrollback. **Open in editor** (`editor-link.ts`): a path link clicked with ⌘ (Ctrl elsewhere), or `open in editor` in the preview's header, opens a split beside the pane whose shell types `e=${EDITOR:-micro}; command -v "${e%% *}" … || { echo <install hint>; e=vi; }; eval "$e +12 'src/a.ts'"` — `$EDITOR`, else `micro`, else `vi`, `eval` because `$EDITOR` can be two words (`emacs -nw`), the path quoted twice for it (`evalArgument`), `+<line>` from a `:line` or `:line:col` suffix, which `splitLineSuffix` strips before `/api/files/stat` is asked so `src/a.ts:12:3` resolves to the file (the link still covers the whole token). **The editor layout**, ⌘⌥E (Ctrl+Shift+Alt+E), the settings button and the intro row: the focused pane keeps its shell, a right split (62 %) types the editor on `.` (micro refuses a directory and opens empty), a lower-left split types lazygit (`editorLayoutPlan`); a missing program prints `kitterm: micro is not installed. brew install micro (macOS); …` (`installHint`) and the editor line falls back to `vi`. **A split's command is typed at the shell's first prompt mark** (OSC 133 A, `TerminalPane.typeInitialCommand`), echoed once; a shell with no marks gets it as type-ahead 2.5 s after the socket opens; it is never persisted, so a reload types nothing. **The pane answers DECRQM** (`decrqm.ts`, `CSI ? Ps $ p` and `CSI Ps $ p`, from `Terminal.modes`, the active buffer and the 1006 tracking; an unknown mode is `0`): xterm.js 6.0.0's own answer throws `i is not defined` in the Vite bundle and ends the parser's write loop, and lazygit asks about four modes before its first frame, so a lazygit pane froze on the shell's last line before this. Proofs: `osc52.test.ts`, `touch-scroll-x10.test.ts`, `editor-link.test.ts`, `path-links-line.test.ts`, `pane-keys-editor.test.ts`, `decrqm.test.ts`
- **Restart resilience**: the daemon polls each shell's cwd via `proc_pidinfo` (~2s, diff-gated) and pushes `cwd` frames, so a restored pane respawns where it was even when the shell emits no OSC 7. Each pane's `?hist=<key>` maps to `~/.kitterm/history/<key>` (set as `HISTFILE`, seeded once from the user's global history), so up-arrow survives a restart with that pane's own commands. A session's name and labels are written to `~/.kitterm/respawn.json` as they change (`RespawnHintStore`, called from the registry actor, capped at 256 entries, entries dropped on removal); a reattach whose id is gone consumes them, so the respawned shell keeps them and a foreman finds `crew:alpha` again under new ids
- **A run says how it ended**: the daemon writes `~/.kitterm/last-run.json` (`LastRun`, `"version": 1`) — `pid`, `startedAt`, `aliveAt`, `sessions`, and on a clean end `endedAt` plus `reason` (`stopped`, `restarted`, `takeover`). `runDaemon` begins the run, reading the previous record first because writing is what destroys it; `DaemonServer.stop()` records `stopped` with the session count taken before the shells go; `prepareHandoff` records `takeover` before the `exec`, so a live upgrade never reads as a death. A 30 s repeated task (`KittermConstants.lastRunRefreshSeconds`) refreshes `aliveAt` and `sessions` from the registry inside a `Task`, off the event loop and off the output path. A run the kernel kills leaves no `endedAt`; that absence is the signal, and it is why `aliveAt` exists — it names when the run was last alive to within one interval. `kitterm restart` reaches the daemon as the same `SIGTERM` `kitterm stop` sends (a plain signal, or `launchctl kickstart -k` under the service), so **the CLI writes its intent before it signals**: `~/.kitterm/stop-intent.json` (`StopIntent`, `"version": 1`) names the pid from the pid file, `restarted`, and `writtenAt`; `DaemonServer.stop()` consumes it on the signal queue, deleting the file on every read, and records `restarted` only when the pid is its own and the intent is under `StopIntent.maxAgeSeconds` (60 s) old, else `stopped`, so a leftover intent never labels a later stop or a kill. `kitterm stop` writes no intent. Under `KITTERM_STATE_DIR`, `restart` takes the stop-and-start path like `stop` and `start`, never the service's `kickstart`. The feed's `previous` stays `clean` for both reasons
- `--lan` binds 0.0.0.0 with token auth for non-loopback peers (`?token=` → cookie; `~/.kitterm/token`); loopback stays trusted. Tokens carry a **grade**: `full` (everything) or `watch` (observe + read API only — never input, never `requestControl`, never spawn; the WS handler takes a watch-only path that can't reach `spawnNew`, and `POST …/input` answers 403). Three token kinds: ephemeral control (`~/.kitterm/token`), ephemeral watch (`~/.kitterm/token-watch`, powers the 👁 watch-link share button via `/api/lan` `watchToken`), and named persistent tokens (`kitterm token create <name> [--watch]`, SHA-256 hashes only in `~/.kitterm/tokens.json`, mtime-cached reload so revocation needs no restart). The auth cookie is set to exactly the presented token — a watch token can never ride a full-access cookie
- `--record` writes asciinema v2 casts to `~/.kitterm/recordings/`
- **Session labels** (`/ws?label=run:abc,node:build`) tag a session so a fleet of shells is attributable to graph nodes. They also declare intent: a labelled session was made by a program, so the registry holds it for `orchestratedSessionLingerSeconds` (1h, `--session-linger`, capped at 24h and validated in `start` where the user can see the error) after its last client leaves instead of the browser's 5 minutes — an orchestrator that crashes and restarts finds its nodes still running. **The clock reaps an idle shell, not a working session** (ADR 0002): at the end of a window, an orchestrated session with a program other than the shell in the foreground (`PtySession.foregroundIsShell`), or with output during the window, gets a fresh window, and the check repeats. A foreman never attaches, so before this rule every crew session was reaped on schedule while `claude` worked in it. An orchestrated shell at its prompt that printed nothing for a whole window still goes, an exited session still goes at the end of its window, and a browser tab's session keeps its 5 minute rule. A program a foreman forgot is held until `kill_session` or `DELETE`; `maxConcurrentSessions` is the bound. **The daemon says which sessions it holds, and never judges them**: the row carries `heldSince` (epoch millis; the first window the session survived, set once, cleared when a client attaches or the session goes), and every survival appends `session.lingered` to the feed with `reason` (`foreground` plus `program`, the row's `foregroundProgram`, from `PtySession.foregroundProgram`, or `output`) and `heldSince`. A foreman compares `heldSince` with its own tolerance and ends what it forgot (`docs/foreman.md`, step 5). `SessionLabels` validates strictly; a malformed tag is dropped rather than failing the connection
- The LAN and watch tokens **persist across restarts** (`~/.kitterm/{token,watch-token}`, 0600). They used to be minted every start, which revoked every share link whenever the daemon came back — including for a routine restart or upgrade, at the moment you are least likely to be at the machine that could print you a new one. A stored token is only trusted if it is owner-readable and looks like one this daemon wrote; anything else is replaced, so a damaged credential fails closed. `--rotate-token` is how you revoke
- `--retain-logs` spills each session's output to `~/.kitterm/logs/<id>.log` (0600, 64 MiB cap, rotating, deleted when the session is reaped) so `/commands/<n>/output` still answers for ranges the 4 MiB ring dropped. **Off by default** — shell output on disk, same reason `--record` is opt-in. All I/O is a `queue.async` hand-off, never awaited on the loop. **The file does not start at stream offset 0** (a shell prints before the session has an id to name a file after), so `SessionLogStore` tracks an `origin` and translates; assuming otherwise returns plausible wrong bytes
- Tab title is per-session (custom name + optional cwd folder), stored per session id; observers adopt the controller's title and cannot edit it. A session created or renamed over the API carries a **server-side name** (`POST/PATCH /api/sessions`), pushed on the `title` opcode; it fills in the tab title when the client has no custom name of its own (the local name still wins)
- `kitterm service install` runs the daemon from a per-user LaunchAgent — see **Service** below
- **Live upgrade** (`kitterm upgrade --live`, `docs/live-upgrade.md`): the daemon execs the staged binary in place. Same pid, same launchd job, same shells; only the sockets die and every client reconnects with `?since=` and gets the exact gap. `POST /api/upgrade/takeover` (loopback + full grade, no body) validates the target with `--help`, answers 200, then the daemon quiesces on the loop, writes `~/.kitterm/takeover/{state.json, rings/<id>.bin}` (`TakeoverState`, `formatVersion` 1: the old binary writes, the new one reads, unknown fields ignored, unknown version refused), sets `FD_CLOEXEC` on every fd but the carried masters (swift-nio sets none on Darwin sockets), and `execv`s `serve … --takeover <dir>`. The successor adopts each master (`PtySession(adopting:)`, no `openpty`, no spawn), restores the ring, the marks, `heldSince`, the recorder and the retained log by path and offsets, registers every session detached with no `session.created`, and continues the event feed in the **same epoch** with `daemon.started {takeover: "true"}`, so a foreman keeps every id. Rungs of the failure ladder: a refused route changes nothing; an `execv` that returns serves on from the same objects (`DaemonServer(config:carrying:)`); an unreadable state boots clean and closes the listed fds; a crash after `exec` is launchd's `KeepAlive`, which is why the CLI refuses `--live` without the service and on Linux. Not carried, by decision: sockets, approval holds, waiters, input in flight, the mark scanner's mid-sequence state
- **Foreman** — `kitterm mcp` is a stdio MCP server that hands an ordinary agent the crew-management toolset (spawn/name/watch/message/wait/note over the HTTP API); the daemon holds no orchestration logic. `docs/foreman.md` is the operating manual and `examples/foreman/` holds reference skills, embedded in the binary as `ForemanSkills` (golden test against the files) and installed by `kitterm skills install` into `~/.claude/skills/<name>/SKILL.md`. The boundary is deliberate: kitterm ships the machinery, the foreman is a prompt
- **The daemon does not emulate a terminal.** No grid, no cursor, no CSI/SGR, no character sets — screen state is entirely the client's business. The one bounded exception is `OscMarkScanner`, which matches OSC 133/633 in the output stream so shell-integration marks exist for sessions nobody is watching (an orchestrator-driven session used to record none, leaving `/api/sessions` state, `lastExit` and `/commands` empty). It scans for two ids and their terminators and nothing else; it runs outside `stateLock` on the event loop, and its cost is below KittermBench's noise floor because it `memchr`s for `ESC` rather than walking bytes. A **rendered screen** exists, but not here: `read_screen` (the MCP bridge) fetches the raw ring tail plus the pane's size from `GET /api/sessions/<id>/output` and renders it in the CLI process with `KittermScreen`, a bounded VT subset that only `KittermCLI` links — `KittermDaemon` has no dependency on it, so the build enforces the rule. `docs/adr/0001-read-screen-in-the-bridge.md` records the decision and the option it closes. `screen_state` (the same bridge) runs `ScreenState`'s pure rules over that same render plus the session row's `foregroundProgram` and answers one of issue #171's eight states with no network call; `unknown` means the rules found no marker, so read the screen yourself before typing. Every answer appends one JSON line — `{at, session, state, rule, source: "rules"}`, no screen text and no matched line's text — to `~/.kitterm/screen-state.log` (`ScreenStateLog`, 0600, rotated to `screen-state.log.1` past 1 MiB, one old file kept, written after the tool has already answered so a failed write never fails the call); `kitterm screen-state stats [--days N] [--json]` reads both files and prints the count per state, the total, and the `unknown` share over the window, no daemon needed. **The unknown capture** (round 4, `corpus/02-clef-decision.md`: the human chose no Clef fallback, so no screen text ever leaves the machine): `kitterm screen-state capture on|off|status` writes `{"captureUnknown": true|false}` to `~/.kitterm/screen-state.json` (0600; off when the file is missing or unreadable; `KITTERM_STATE_DIR` moves it), and while it is on the bridge, after an `unknown` answer has gone out and its log line has landed, writes the rendered screen text the rules saw (`ScreenStateReport.Answer.lines`, the same `lines(styles: true)`) to `~/.kitterm/screen-unknown/<time>-<session>.txt` (`ScreenStateCapture`; the time in the ISO 8601 basic form in UTC, `20261022T071530.123Z`, so the name holds no colon and sorts by time; the directory 0700, the file 0600 through `O_CREAT|O_EXCL`, a `-2` … `-9` suffix for a second sample of one session in the same millisecond) under a six-line header (`kitterm screen-unknown sample`, `at:`, `session:`, `program:`, `size: 120x40`, `rule:`) and one blank line; at most 50 files and 2 MiB together, the oldest by name removed first and the newest never removed; a known state writes nothing; every error is swallowed, so a failed write never fails, changes or delays the answer. **A sample is the pane's screen as it was, so it can hold a secret the pane showed**; the files are read by nothing but `kitterm screen-state samples [--print N] [--json]` (newest first: the index, the time, the session, the program, the size and the bytes, tab-separated; `--print N` prints the Nth file whole) and removed by `kitterm screen-state samples --clear`; `stats` ends with `samples: <count> (capture on|off)` and its `--json` carries `samples` and `captureUnknown`
