## Effects

- **The file.** `~/.kitterm/last-run.json`, version 1, one object, epoch
  milliseconds in the house style: `{version, pid, startedAt, aliveAt,
  sessions, endedAt?, reason?}` with `reason` one of `stopped`,
  `restarted`, `takeover`. Three states, and the third is the point: an
  end time with a clean reason means the run ended on purpose; an end
  time with `takeover` means the daemon replaced itself and kept every
  session; **no end time at all means the run never got to write one**,
  and that absence is the whole signal.
- **Where it is written.** `runDaemon` begins the run and reads the
  previous record before replacing it, returning it for capability 2.
  `stop()` writes `stopped` with the session count taken before the
  shells go. `prepareHandoff` writes `takeover` before the exec, so a
  live upgrade is never mistaken for a death. A thirty-second repeated
  task refreshes `aliveAt` and `sessions` inside a `Task`, off the event
  loop and off the output path.
- **The killed case, proved with a real process.** The test spawns
  `kitterm serve` on a free port under `KITTERM_STATE_DIR`, waits for a
  record naming that pid rather than for health or a sleep, asserts there
  is no end time while it runs, sends `SIGKILL`, waits for exit, and
  reads the record back: pid, start and alive times present, end time and
  reason absent.
- persistent: seven files, two of them new, all Free tier. Twelve tests
  in `LastRunTests.swift`.

## Two decisions the crew flagged, and the foreman's ruling

1. **`aliveAt` is not in the plan's field list.** The crew added it
   because completion condition 2 and corpus request 01 both need the
   time the previous run was last alive, no other field answers it, and a
   file's mtime is not a contract. It is late by at most the refresh
   period and never early. The plan says the file carries at least the
   listed fields, so this is inside the brief. Accepted.
2. **Nothing writes `restarted`.** `kitterm restart` reaches the daemon
   as the same `SIGTERM` that `kitterm stop` sends, so the daemon cannot
   tell them apart from inside; the CLI would have to write its intent
   before it signals. Both are clean ends, so capabilities 2 and 3 lose
   nothing by the gap. The value stays in the vocabulary because a reader
   must accept it. Recorded as a proposal rather than fixed here.

The crew also deviated from the prompt's instruction to hang the refresh
on an existing periodic task: there is no daemon-wide one. The two that
exist are per session and per connection, and both are absent exactly
when the daemon is idle, which is when a memory-pressure kill is
likeliest. Adding one repeated task is the right call and the reasoning
is recorded here.
