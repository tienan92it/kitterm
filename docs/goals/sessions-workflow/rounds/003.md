## Effects

- behaviour: `KnowledgeBase` keeps one cache per registered root. A
  read refuses a base name that starts with `-` or that
  `git check-ref-format --branch` changes, then runs `git -c gc.auto=0
  -c maintenance.auto=false fetch --quiet --no-tags
  --no-write-fetch-head --no-recurse-submodules -- origin
  +refs/heads/<base>:refs/remotes/origin/<base>` with
  `GIT_TERMINAL_PROMPT=0`, `GIT_ASKPASS=true`,
  `GIT_NO_REPLACE_OBJECTS=1` and `GIT_SSH_COMMAND=ssh -oBatchMode=yes`,
  then one `git ls-tree` and one `git cat-file --batch` at that commit.
  Modes 120000 and 160000 are skipped; the caps and the slug rule are the
  disk reader's, through one shared `assemble`. A failed fetch keeps the
  local `origin/<base>` and names the failure and the last good fetch;
  the working tree answers only with no local base. Reasons carry exit
  codes, never git's stderr.

## Correction

The review of 7976784 found a blocker: the base name comes from the
remote's `origin/HEAD` and reached `git fetch` as an option. A default
branch named `--depth=1` made the clone shallow (reproduced on git
2.39.2), and `--upload-pack=<path>` runs a program on a file remote. It
also found that the fetch replaced the human's `FETCH_HEAD`, that it
could recurse into submodules and run maintenance, that an ssh remote
could prompt each minute, and that a failed fetch dropped to the working
tree. The crew fixed all of them in 2411fc0.

## Reflection

goal does until PR #185 merges, does not show; a goal folder that is
only in the working tree no longer shows once `origin/<base>` is read.
The proposal in `STATE.md` closes both. A fetch moves the human's
`origin/<base>`, so `git status` in the checkout says "behind" after a
