# kitterm HTTP API

This file holds the section `AGENTS.md` carried until 2026-11-10 (goal `lean-context`), moved here unchanged. A round that changes this surface updates this file.

## HTTP API (JSON off the I/O stream; read-only unless noted)

- `GET /api/health`, `GET /api/lan`, `GET /api/sessions` (mark-derived state per session; `?label=run:abc` filters, and each row carries its `labels`, its `name` and `note` when set; a filter that is not `key:value` is a 400, because an empty list would read as "that run has no sessions"). Each row also carries a **`mergedState`** — the crew vocabulary `working / needs-approval / needs-input / completed / failed / idle / exited / unknown` — plus `agent {status, message?, at}` (the session's latest hook report), `pendingApproval`, and `lastOutputAt`. `mergedState` is `MergedSessionState.merge`: after the two hard facts (`exited`, `needs-approval`) **the newer evidence source wins** — the latest hook report or the latest state-bearing mark. That is what makes a shell running `claude` work: its marks say "running" for hours (one preExec, no commandEnd until claude exits), every hook report is newer, so `working`/`needs-input`/`completed` track the agent's real turns; a human's later command produces newer marks, which then win. Never a state machine the daemon advances, so a session with no Claude hooks collapses to the exact `running/idle/unknown` (`state`, still sent) it always had. `lastOutputAt` is a fact for a caller's own "stuck" judgment; the daemon ships no such judgment itself. **`foregroundProgram`** is the name whatever took the terminal from the shell was started under (`claude`, `vim`, `cat`), and is absent when the shell itself is reading or nothing holds the tty yet — a pane running `claude` and a bare `zsh` used to look the same in `list_sessions`. The name is the leader's `argv[0]` (ADR 0004: `KERN_PROCARGS2` on Darwin, `/proc/<pid>/cmdline` on Linux), last path component, less a login shell's `-`, with the executable basename as the fallback — `~/.local/bin/claude` execs `~/.local/share/claude/versions/2.1.263` and keeps its pid and argv, so the executable path read `2.1.263` where the row must say `claude`. It is the same `tcgetpgrp` read as `foregroundIsShell`, made when the row is built, so the output path never pays for it and the value is never stale. **`agentSessionId`** and **`agentTranscript`** are the join to the Claude Code session that ran in the shell: every hook payload carries `session_id` and `transcript_path`, and `handleHookEvent` keeps both on the session (`PtySession.recordAgentJoin`, an `AgentJoin`) from every hook, blocking or not, so whichever of the four arrives first sets them and a second `claude` in the same shell replaces them; a hook from another project that names a pane with a join is refused (see `POST /api/hooks`). The path is stored as the hook gave it — absolute, under `~/.claude/projects/` — the way the row's `cwd` and `shell` are; the cost route reads its last line and the session list reads its tail for the model (**`agentModel`**, below). Both fields or neither: a session that never ran `claude` has neither, and a hook with half a join changes nothing. They survive a live upgrade with the session **`agentModel`** and **`agentModelName`** are the model the session runs on: the `message.model` of the last `"type":"assistant"` line of `agentTranscript`, as Claude Code wrote it (`claude-fable-5-1`) and as the fleet view prints it by the naming rule of `design/foundation.md` (`Fable 5.1`, `Opus 5 · 1M`, `Haiku 4.5`; an id the rule does not fit prints unchanged, `ModelName`). Absent, both, until the session has an assistant turn, and on a `"<synthetic>"` line: never a guess. `TranscriptModel` reads one 256 KiB `pread` of the tail on `TranscriptBill.queue`, off the loop and off the registry actor (measured 2026-09-18 over the 40 newest transcripts: the last assistant line sits within 4 KiB in 3, within 64 KiB in 39, within 256 KiB in all 40), and `TranscriptModelCache` keys the answer by path with the file's size and mtime, so a session list costs one `stat` per session with a transcript and a read only of a file that grew; a grown file whose window holds no assistant line (a long tool result) keeps the model the path last yielded.
- **Projects** (`Projects.swift`): every session row carries **`project {id, name, root, registered}`** and **`orchestrated`** (true for a labelled or API-spawned session). The daemon resolves the project from the session's cwd: the nearest ancestor of the cwd that is either a git checkout or a registered root in `~/.kitterm/projects.json` (`{version: 1, projects: [{id, name, root, knowledge?}]}`, `knowledge` defaults to `docs/goals`, written by `kitterm project add|init|list|remove`; `kitterm goal new|list` reads and writes the goal folders under it without touching the file, reloaded on mtime change like `tokens.json`) wins. The walk looks for `.git`, following a `gitdir:` file one level so a worktree resolves to its main checkout, bounded at 32 levels; the checkout names the project unless a registered root sits inside it, nearer to the cwd, or is the checkout itself. Outside every checkout the longest registered root that is a prefix of the cwd wins; else no `project` field. A registered root is a name and a configuration for one root, not a claim over everything beneath it: a checkout under a registered parent is its own discovered project (`docs/goals/foreman-harness/corpus/02-nested-checkout.md`). A discovered project's `id` is a slug of its folder name, `registered` false. A `project:<id>` label overrides the resolution (a registered id carries the registered project; an unknown one is reported as itself). The reserved label keys are the Labels table in `docs/goals/LOOP.md`; `SessionLabels` names them as constants. Roots are stored as `realpath`s because the kernel reports a cwd as `/private/var/…`. The resolution runs only when the cwd or the file changed (`PtySession.project(forCwd:)`, from the cwd poll and from the listing row for a detached session the poll does not cover), never on the output path
- `GET /api/projects` — the identity of every project seen, `{id, name, root, registered, knowledge, pullRequestBase?}`: registered (with no session too) or discovered from a live session's cwd. `pullRequestBase` is `https://github.com/owner/repo/pull/` when the root's `origin` remote is on GitHub (`PullRequestBase.parse` reads `git@github.com:owner/repo.git`, `ssh://git@github.com/owner/repo.git` and `https://github.com/owner/repo(.git)`, and an SSH config host alias after `github.com`, `git@github.com-work:owner/repo.git`, `[A-Za-z0-9_-]` with no `.`, so `github.com.evil.example` stays another host; `RemoteOrigins` runs `git remote get-url origin` once per root every five minutes on its own queue, never on the loop) and absent for any other remote or none, so the fleet view prints the PR as plain text. No counts: the fleet view counts what it shows from the session rows, and a count here was a second merge per session per poll and an archive walk per tick that nobody read. Read-only, any grade. **`?project=<id>`** filters `GET /api/sessions` and `GET /api/archives` (an unknown id is an empty list, a malformed one a 400, like `?label=`); each archive row carries its `project` from its labels, then its archived cwd. The MCP tool `list_projects` proxies the route and `list_sessions` takes `project`
- `GET /api/projects/<id>/pulls` — **the pull requests of the project's GitHub repository** (`PullRequestStatus`, round 2 of `sessions-workflow`): `{ok, project, readAt?, ageSeconds?, reason?, pulls}`, each pull `{number, title, state, draft, headRefName, mergedAt?, url, ci?, additions, deletions, createdAt?, updatedAt?}` in the order `gh` printed them. `state` is `open`, `closed` or `merged`; `ci` is one word reduced from `statusCheckRollup` (`PullRequestStatus.ciWord`): `failing` when any check failed (a `CheckRun` conclusion of `FAILURE`, `TIMED_OUT`, `CANCELLED`, `ACTION_REQUIRED` or `STARTUP_FAILURE`, a `StatusContext` state of `FAILURE` or `ERROR`), else `pending` when any check has not ended, else `passing`, and absent with no checks. The source is `gh pr list --repo <owner/repo> --state all --limit 50 --json number,title,state,isDraft,headRefName,mergedAt,url,statusCheckRollup,additions,deletions,createdAt,updatedAt,isCrossRepository` (`isCrossRepository` is kept on the pull for `KnowledgeBase.goalBranches` and is not in the answer; `createdAt` and `updatedAt` are the strings `gh` printed, `2026-10-06T08:10:36Z`, absent when it printed none. The time a pull request left draft is not in `gh pr list`, so the fleet view counts a ready pull request's wait from `updatedAt`: a push, a review or a label moves it, and the wait is never longer than the true one) for the `owner/repo` of the project's `pullRequestBase`, with the human's own `gh` login: no token file, no REST client. **A request never waits for `gh`**: it answers what the cache holds under a lock and calls `refreshIfDue`, which starts one read on the serial queue `kitterm.pulls` when no read of that repository is claimed and the last one ended the repository's interval ago or more, so a page that polls every two seconds costs no `gh` on the event loop. **The interval is adaptive** (round 8 of `sessions-workflow`, `corpus/03-faster-pull-sync.md`; `PullRequestStatus.interval`, pure): `activeSeconds` (15) while the repository has open work — an open pull request whose `ci` is `pending`, a pull request whose `updatedAt` is under `recentSeconds` (5 min) old, or a live session labelled `pr:<N>` for one of its open pull requests (the registry's `labelledPulls()`, one call per request, handed with the project id; the knowledge route hands no labels and keeps the last ones) — else `idleSeconds` (180). The interval counts from the end of a read, so a repository whose `gh` takes its whole timeout to fail is not due again when it ends. The first request for a repository therefore answers an empty list with `reason: "not read yet"`. **A nudge reads at once** (`PullRequestStatus.nudge`, `PullNudge.swift`): a command that ends in a session whose project has a `pullRequestBase` and whose command line matches `git push …` or `gh pr create|merge|ready|close|edit|review …` as a command of the line (`PullNudge.commandNudges`: split on `&&`, `||`, `;`, `|` outside quotes, leading `VAR=value` words skipped, so `git pushd` and `echo gh pr create` match nothing; a command with no known command line nudges nothing), and a note on `POST /api/sessions/<id>/events` from such a session whose first line starts with `PROGRESS ` or `DONE ` (`PullNudge.noteNudges`, the protocol of `docs/foreman.md`). The session's command end reaches `PullNudger` through the registry (`setCommandEndedListener`, `PtySession.setCommandEndedHandler`, the paired command with its line, once per `commandEnd` mark); the matcher runs where the event lands and the project, the remote and the read run on `RemoteOrigins.queue` and `kitterm.pulls`, never on the loop. The read starts `nudgeGapSeconds` (5) after the last read's start at the earliest, one read at a time per repository; a nudge while a read runs queues exactly one more after it, a nudge while one waits changes nothing. **The ceiling**: `readsPerMinute` (24) list reads a minute daemon-wide, nudges included, a sliding window of starts; past it a read waits for the next slot (the budget: 7 repositories all active at 15 s is 1,680 GraphQL calls an hour against the 5,000-point budget every crew's `gh` shares; the ceiling caps the daemon at 1,440). **A read whose pulls or reason differ from the last appends `pulls.changed` with `data {project}`** to the event feed, one event per project that asked for the repository, never on an unchanged read (the comparison is the answer less `readAt` and `ageSeconds`, since `readAt` moves on every read); the fleet view, parked on `/api/events`, marks that project's entry stale and asks its pulls at once with `If-None-Match`, keeping its 10 s poll as the fallback (`sessions-pulls-changed.test.ts`); a watch page never asks pulls, so the event changes nothing there. Each `gh` leads its own process group (`posix_spawn` with `POSIX_SPAWN_SETPGROUP`) and has a 20 s timeout (`timeoutSeconds`): the group gets `SIGTERM`, then `SIGKILL` 1 s later, so a `gh` that ignores the first signal cannot hold the queue. One thread reads both pipes and reaps the process; once `gh` has ended the pipes are read for 0.5 s at most and then closed, so a child of `gh` that keeps one open holds nothing and what was read is judged. `gh` is looked for in the absolute entries of the daemon's `PATH`, then in `/opt/homebrew/bin`, `/usr/local/bin` and `~/.local/bin` (`defaultSearchPath`), because launchd starts the service with `/usr/bin:/bin:/usr/sbin:/sbin`. `reason` says why the latest read gave no list: `no GitHub remote` (no `gh` runs), `not read yet`, `gh is not on PATH`, `gh is not logged in` (the list failed and the local `gh auth token` exited non-zero too; that check asks no server, so an offline machine is not logged out, it runs only after a failed list, and its stdout goes to `/dev/null`, so the token is never read, kept or logged), `gh pr list exited <code>: <first stderr line>`, `gh pr list timed out after 20 s`, `gh pr list printed no JSON list`. A failed read keeps the last good list; `readAt` (epoch milliseconds) and `ageSeconds` are then the time and the age of that last good read, and both are absent before the first good read. The `ETag` covers the body less `ageSeconds`, which changes every second, and `If-None-Match` answers 304. The project is a registered id, else the id the store gave a root a session's cwd discovered in this run (`ProjectStore.discoveredRoot`, one lock take, no session listing per poll); any other id is 404, an id only a `project:` label names included. 503 in a handler built without the cache. **Full grade only**: the titles and the branch names of a repository are not what a watch link shows. The fleet view reads it for the `REVIEW` line and each goal line's state words (see **Fleet view**). **The change probe** (round 9, `corpus/04-change-probe.md`) answers a change on github.com and a crew's `gh pr create` or `git push`, which `PullNudge` never sees because Claude Code's Bash tool runs outside the pane's shell: while a full-grade page has asked this route for a repository in the last `watchSeconds` (30), `PullRequestStatus.watch` keeps it probed every `probeIntervalSeconds` (5) with a conditional `gh api -i -H 'If-None-Match: <etag>' repos/<owner>/<repo>/pulls?state=all&sort=updated&direction=desc&per_page=5`, on its own queue, `probeQueue` (concurrent, so one repository's slow `gh` never delays another's tick; `probeArmed` keeps at most one probe scheduled or running per repository), never the event loop and never `kitterm.pulls` while a list read of the same repository is in flight. A `200` with a changed `ETag` stores it and reads at once through the same `nudge(repository:)` as a local push, inside the one-read-at-a-time rule and the `readsPerMinute` ceiling above; the first `200` only stores the tag. A `304` costs nothing and starts no read; a failure backs the repository off to `probeBackoffSeconds` (60), and a later success resets it to `probeIntervalSeconds`. A pending check still reads at its own `activeSeconds` (15) pace, since a finished check does not change `updatedAt`; the probe changes no field of this route's answer. No MCP tool proxies the route yet
- `GET /api/projects/<id>/knowledge` — `{ok, project, source, sourceReason?, goals}`: one summary per goal folder of the project's knowledge package (`docs/goals/`, or the registered `knowledge` directory), **read from the merged base branch, not from the working tree** (`KnowledgeBase`, round 3 of `sessions-workflow`), because nobody pulls the main checkout after a merge. For a root with an `origin`, one read runs `git -c gc.auto=0 -c maintenance.auto=false fetch --quiet --no-tags --no-write-fetch-head --no-recurse-submodules -- origin +refs/heads/<base>:refs/remotes/origin/<base>` on the serial queue `kitterm.knowledge-base`, where `<base>` is what `git symbolic-ref --short refs/remotes/origin/HEAD` names, else `main`, else `master` when `origin/master` exists and `origin/main` does not. **The base name is the remote's, so it is data**: a name that starts with `-` or that `git check-ref-format --branch` does not answer unchanged is refused before any fetch (`the base branch name is refused: <name>`; a default branch named `--depth=1` once made the clone shallow), and the fetch names the branch only inside the full refspec after `--`. That refspec writes `origin/<base>` in a single-branch clone too, and the human's `FETCH_HEAD` is never replaced. The read then builds the summaries from the tree of `origin/<base>` through git objects with no checkout: one `git ls-tree -r -t -l -z <commit> -- <knowledge>` and one `git cat-file --batch` for the `STATE.md`, `goal.md` and `rounds/<N>.md` blobs the listing names (`KnowledgeFile.assemble` builds the summary for both sources, so the two cannot differ). The daemon writes no working tree, no index and no `HEAD`; the fetch moves remote-tracking refs only. The tree reader keeps the rules below: the same slug rule, the same 64 folders and 256 KiB, and a tree entry of mode 120000 (a symlink) or 160000 (a submodule) is refused and skipped like a symlink on disk, the knowledge directory itself included. Only the knowledge directory is listed, and only an object that listing names is read. An unchanged listing keeps the last summaries and reads no object. **A request never waits for the fetch**: it answers what the cache holds under a lock and calls `refreshIfDue`, which starts a read when none runs and the last one ended `KnowledgeBase.refreshSeconds` (60) ago or more, so a merge shows within two poll minutes. `git` runs through `PullRequestStatus.run` (its own process group, a 20 s timeout, stdin from a scratch file removed when the run ends) under `KnowledgeBase.environment`, where nothing can ask a human and an object id reads the object it names: `GIT_TERMINAL_PROMPT=0`, `GIT_ASKPASS=true`, `GIT_SSH_COMMAND=ssh -oBatchMode=yes` (it replaces one the daemon inherited: a fetch that needs the human's own ssh command fails with its exit code), `GIT_NO_REPLACE_OBJECTS=1`, `GIT_LITERAL_PATHSPECS=1`, and is looked for like `gh`. `source` is `origin/main` (the base's name) or `working tree`. **A fetch that fails keeps reading the `origin/<base>` the checkout already holds**: `source` stays `origin/<base>` and `sourceReason` names the failure and the last good fetch, `git fetch exited <code>; last good fetch 2026-10-05T09:20:00Z` or `git fetch timed out after 20 s; no good fetch yet` (the code alone: a fetch's stderr can hold a remote URL with a credential, and the route answers at watch grade; the time is the fetch's, so the `ETag` holds between two failures). With `working tree`, the summaries are the checkout's files as before and `sourceReason` says why: `not read yet` (the first request), `no origin remote` (also a root that is no checkout), `git is not on PATH`, `the base branch name is refused: <name>`, `git fetch exited <code>; no local origin/<base>`, `origin/<base> is missing`, `no docs/goals directory on origin/<base>`, `docs/goals on origin/<base> is over 64 MiB`, `no base branch reader` in a handler built without one. **A goal on an open goal branch is read from that branch** (round 4 of `sessions-workflow`): a goal lives on `goal/<slug>` until its pull request merges, so the route takes the open pull requests of the project's GitHub repository from the cache of `PullRequestStatus` (a lock take; the route also schedules that cache's `gh` read, so a page that never asks the pulls route feeds it), keeps those whose `headRefName` is `goal/<slug>` with a valid goal slug (`KnowledgeBase.goalBranches`, `ProjectStore.isValidID`, one per slug in `gh`'s order; a pull request from a fork, `isCrossRepository`, is skipped before the count and the dedupe, because its head is no branch of `origin`), and hands them to the minute's read. That read names the base and every such branch in the one fetch, each as `+refs/heads/goal/<slug>:refs/remotes/origin/goal/<slug>` after `--`, with the same flags and environment; a branch name passes the base's rule first (no leading `-`, `git check-ref-format --branch` answers it unchanged), and a refused name reaches no fetch. A fetch that names a branch the remote does not hold fetches nothing, so when the one fetch exits non-zero with a branch in it, the read fetches each ref alone (a timeout gets no second try). **A branch the remote does not hold is not read**: when its fetch alone exits non-zero while another ref's fetch alone succeeds, its local `origin/goal/<slug>` is an earlier goal's and the base's summary answers; when every fetch fails (offline), the local refs are read with the reason, as the base is. **The fetches of one read share 30 s** (`KnowledgeBase.fetchBudgetSeconds`): once they are spent no further fetch starts and the refs left read what is here with `git fetch not tried: the 30 s of the read are spent`; the fetch that runs when the budget ends keeps its own 20 s timeout, so the fetches of one read end within 50 s. The read then lists `<knowledge>/<slug>` alone at the commit of `origin/goal/<slug>` (a literal pathspec) and builds that one summary with the tree reader, the caps and the modes of the base, so nothing else the branch holds is listed or read; a branch with no such folder, with a symlink there, or with no regular `STATE.md` yields nothing. **At most 8 branches per project** (`KnowledgeBase.maxGoalBranches`, the first 8 open ones as `gh` printed them): each adds a refspec to the fetch and three local `git` commands to the read on the one serial queue, and one round of a goal runs at a time. **Every goal carries its own `source`** (`KnowledgeBase.Snapshot.merged`): a branch's summary replaces the base's of the same slug and carries `source: "origin/goal/<slug>"` and `pullRequest` (the number), plus `sourceReason` (`git fetch exited <code>`) when its fetch failed and the local ref was read; a base goal carries the base's name; a goal folder that only the working tree holds, on no base and no open branch, is kept with `source: "working tree"`, so the working tree is read for every answer again. A merged or closed pull request names no branch: the next read drops it and the base's summary answers. The schedule holds: a new branch list starts no second read inside the minute, so a branch shows up to two minutes after its pull request opens (one minute of the pulls cache, one of this one). `chore/<slug>` branches are not read: a chore has no goal folder. Each summary is parsed by `KnowledgeSummary` with no Markdown renderer: `slug` (the folder name; the `# STATE:` heading does not decide it), `goal` (the first `# ` heading of `goal.md` less `Goal:`), `status`, `round` and `budget` (the `- Status:` and `- Round: N of M` lines), `lastFloor`, `nextAction` (the first paragraph of `## Next action`, 512 bytes), `proposals` (top-level bullets under `## Proposals waiting on the human`), `lastRound` (the highest `rounds/NNN.md`), `lastRecord` (`<slug>/rounds/NNN.md`, the path the file route serves), `lastDecision` (the first line of that record's `## Decision`), and the goal's cost as the sum of every record's `- Cost:` line (`LOOP.md`'s shape, `KnowledgeSummary.costLine`, the parser `kitterm goal cost` reads with too): `costUSD`, `inTokens` (input, cache creation and cache read) and `cacheReadTokens`, all three absent for a goal whose records carry no line, so a goal that predates the bill prints no number rather than a zero; a record over the 256 KiB cap counts no cost. `rounds` is one entry per `rounds/<N>.md`, by number: `{number, task?, started?, costUSD?, durationMs?, pr?, correction}` — the queue item after `# Round NNN:`, the `YYYY-MM-DD` the `- Started:` line begins with, the record's `- Cost:` lines summed, the `PR #N` a `- Result:` bullet names, else the one after `Result:` on the `- Base:` line, and whether its `## Correction` section says one happened (`KnowledgeSummary.isCorrection`: `true` when the section's text, after list marks and spaces, is not empty and does not start with `None` in any case; an absent section, an empty one and a `None` one answer `false`, so the heading alone counts nothing); absent for a goal with no record. `tasks` is the goal's task list (`KnowledgeSummary.tasks`): one `{slug, state, round?, pr?}` per slug listed under `## Queue` (`pending`), `## Failures` (`failed`) and `## Done` (`done`) of `STATE.md`, in that order, each slug once; an item is a column-0 `- `, `* ` or `N. ` line, its slugs are the backticked kebab words on its first line before the first comma (so `` `a` (1) and `b` (2), round 1, `9784fd2`.`` yields `a` and `b` and not the sha), and `round N` and `PR #N` come from that first line; prose under a heading (`None.`) names no task; a slug in two sections keeps the state a reader needs most, `failed` over `pending` over `done`, at its first position; the key is absent when `STATE.md` has none of the three headings and an empty list when a heading lists nothing. `working` is never in the file: the page joins it from a live `task:` label. A goal folder is a direct child of the knowledge directory whose name is a slug (`ProjectStore.isValidID`, the rule `kitterm goal new` enforces), that is a real directory holding a regular `STATE.md` (`KnowledgeFile.summaries`): a child with another name or without a `STATE.md` is skipped, a symlinked child or `STATE.md` is refused and skipped like every other symlink, and at most 64 folders are read, in name order. The listing opens the knowledge directory once and each goal folder once and reads `STATE.md`, `goal.md`, `rounds/`, and every `rounds/<N>.md` relative to that descriptor; `kitterm goal list` calls the same listing. The order is `active`, `waiting`, `stopped`, `done`, then any other status, then by slug (`KnowledgeSummary.isOrderedBefore`, the comparator `kitterm goal list` sorts with too); a package with no goal folder answers an empty `goals`. A missing file or line leaves its field absent; a malformed file is never an error. Answers with an `ETag` over the whole body and honours `If-None-Match` with 304, so the fleet view's poll repaints nothing for an unchanged package. 404 for a project with no knowledge directory. Read-only, any grade (see **Security**)
- `GET /api/projects/<id>/knowledge/<path>` — one file under the knowledge directory, read-only and jailed (`KnowledgeFile`), **from the source the summary route names**: when the cache holds the tree of `origin/<base>`, the file is the blob of that commit (`KnowledgeBase.file`), found by a walk of the cached listing with the same answers (a symlink anywhere in the chain is 404, a directory, a submodule or a missing path is 404, a blob over 256 KiB is 413) and read by its object id with one local `git cat-file blob` on the knowledge queue, never a fetch, so a file only the working tree holds is 404 there; a path under a goal that an open branch holds (`<slug>/…`) is walked in that branch's listing and read from that branch's commit with the same answers, and a path under a goal folder the base does not hold is read from the working tree when the summary lists that goal (the folder holds a regular `STATE.md`; any other working-tree folder stays 404 there); otherwise the working tree, as follows. The project must be a registered one; a discovered project answers 404 on both routes. The store lookup runs in the task off the loop; every read runs on one serial knowledge queue and hops back with `Data`; the loop never touches the disk or the store lock. - `GET /api/events?since=<seq>&timeout=<s>&session=<id>` — the **daemon-wide control-plane feed**, so a foreman watching a dozen crew sessions holds one parked request instead of polling `/api/sessions` for each. Returns events newer than `since` at once, or parks until one arrives (the `/commands/<n>/wait` shape — one loop, no streaming machinery), answering `{ok, epoch, events, next, pruned}`. `next` is the cursor to poll with; `pruned` is true when `since` aged out of the bounded ring (the `/commands` 410-honesty, without killing the poll loop). `epoch` is the daemon process's random id (`EventLog.epoch`): a restart resets `seq`, so a cursor alone cannot tell "quiet" from "the daemon I was watching is gone". A caller sends `epoch=` back; a mismatch — or a `since` past this daemon's head, which this daemon never issued — answers at once with `pruned` true and the new epoch's events from its first, `daemon.started` (`{epoch, version, pid}`, plus `takeover: "true"` when a live upgrade continued the epoch, plus **the previous run's summary** when the state directory held a record: `previous` (`clean` for a `kitterm stop` or `restart`, `takeover` for a live upgrade, `unrecorded` for a run that never wrote an ending — the kill this feed exists to explain), `previousPid`, `previousAliveAt`, `previousSessions`, and `previousEndedAt` when there was an ending. The keys are `previous`-prefixed because `pid` on this event means *this* run's pid, and `previous` is absent exactly when there was no record, so a first start needs no special value. `server.log` carries the same fact as one line. Appended by `DaemonServer.init` from what `LastRunStore.beginRun` handed `runDaemon` (`LastRun`, `PreviousRun`)). Read-only, any grade — observing what agents do. v1 event types: `daemon.started`, `session.created/renamed/exited/lingered/removed`, `agent.status`, `agent.join-mismatch`, `approval.pending/resolved`, `command.failed`, `note`, `pulls.changed`. `pulls.changed` carries `{project}` and no session: a `gh` read changed that project's pull request list or reason (see `GET /api/projects/<id>/pulls`). `agent.join-mismatch` carries `{sessionId, cwd, transcript}` of a hook the pane it named refused (see `POST /api/hooks`), once per refused Claude Code session per pane. `command.failed` carries `data` `{index, exit, command?}` (strings, like every event's data) for a non-zero `commandEnd` in an orchestrated session only, naming the command the mark itself closed; `index` is `/commands`'s, so `/commands/<index>/output` reads what it printed; nothing for exit 0 or a browser tab's session. `session.created` carries `respawnOf` when a pane's reattach found its id gone and got a fresh shell. The feed is `NIOLock`-guarded, not loop-confined: `SessionRegistry` (an actor) appends lifecycle events from off-loop, and completing a parked promise cross-thread is NIO-safe. Read-or-park happens under one lock (`EventLog.poll`), so an off-loop append cannot land between "nothing yet" and "park me" and strand the request; a `since` past the head answers at once as pruned, with the true `next`, rather than parking to its deadline. Waiters are capped daemon-wide (503 past the ceiling) and the timeout ceiling is `eventWaitMaxSeconds` (60), lower than a command wait's, because this route is any-grade

- `PUT /api/files/content?path=<file>&session=<id>` — **the save** (`FileEdit`, `code-editor` round 3, phase 2a of ADR 0005): the body is the new bytes of one existing regular file inside a project, written as sent (no line-ending or BOM change), capped at the read cap (256 KiB; 413 above it through the body-cap predicate `isEditorSave`). Answers 200 `{ok, etag, bytes, path}` with the new `ETag`. **The first HTTP route that writes outside `~/.kitterm/`**, so these are its rules. Full grade only, no `--agent-control` (a person saving their own file in their own browser, the drop route's and `PATCH`'s argument). CSRF: `X-Kitterm-Editor: 1` is required and `Origin` must equal the request's own scheme and host exactly (`http://127.0.0.1:3418`; `https` on the TLS listener or behind a proxy that reports it), 403 otherwise, and no CORS header is ever answered. Precondition: `If-Match` is required (428), the `ETag` the read gave; a mismatch is 412 with the current `ETag` in the header and in the body, so the page can compare; a bare tag matches, a weak one or a list does not. The path resolves like the content route's but lexically (`FileEdit.resolve`: `~`, the session's cwd, `.` and `..`, no symlink followed); the project is the one of the parent directory's real path (the cwd rule of `ProjectStore`: the nearest checkout or registered root); the jail root is that root's stored `realpath`; the components walked are the ones below the shortest ancestor of the lexical path whose `realpath` is the root (`FileEdit.jail`), so a symlink above the root is allowed (`/tmp/x/a.ts` saves into the project at `/private/tmp/x`) and a symlink anywhere below it is 403. A path under no project is 403 `outside every project`. The walk opens the root by its path and every component with `openat` relative to the one before, `O_NOFOLLOW_ANY` on Darwin (alone: with `O_NOFOLLOW` beside it the kernel answers `EINVAL`, measured on macOS 26.6.2), `O_NOFOLLOW` on Linux, so a symlinked parent, a symlinked target and a dangling symlink are 403 `a symlink in the path`; a component named `.git` in any case at any depth, and any directory whose `(st_dev, st_ino)` is the root's `.git`, is 403 `under .git`; the target must exist (404; no create this round) and be `S_ISREG` with `st_nlink == 1`, else 409 `not a regular file` or `hard-linked file` (the rename would split the link). - `POST /api/sessions/<id>/archive` — **cold storage.** Persist a finished session's evidence (metadata, commands, marks, output) to `~/.kitterm/archive/<id>/{archive.json, output.log}`, then end it. Destructive, so `--agent-control` + full grade like `DELETE`. Honest scope: it preserves what a session *did*, never what it *was* — there is no process to restore. "Resume" is a foreman convention (spawn a new session with the archived name/cwd and a `resumed-from:<id>` label), not a restore. `archive.json` is versioned (`"version": 1`), the same on-disk discipline as the live-upgrade handoff. - `POST /api/hooks` — **an agent asks a human, and reports on itself.** A Claude Code `"type": "http"` hook posts its event here; for **`PermissionRequest`** the daemon **holds the response** until someone allows or denies, and the verdict travels back in the body (`hookSpecificOutput.decision {behavior, message}` — verified against Claude Code 2.1.260: allow ran the tool, deny refused it with the message shown) — status codes cannot block a tool call, only the JSON can. `PermissionRequest` is the held event because it fires **only when Claude would show a dialog**: an auto-allowed tool never reaches the daemon, so nothing that would not have waited on a human is slowed. **`PreToolUse` is never held** — it fires for every tool call, allowed or not, and holding it made an always-on hook unusable (every Read and Edit in a pane waited up to five minutes; An hit this within the hour of installing it). It records the `working` edge and answers `{}` at once. This is the one route that answers slowly on purpose, reusing the `commands/<n>/wait` machinery so nothing blocks the loop. **No decision is an answer**: on expiry it replies `{}`, and the agent shows its own dialog in its pane, so an unattended agent is never wedged. The pane is named by `X-Kitterm-Session`, which the hook config reads from `KITTERM_SESSION_ID` — exported into every shell the daemon spawns, because a hook config is static and cannot look it up. `Notification` records `needs-input` (carrying its `message`), `Stop` records `completed`, both answer `{}` at once — that is the `agent`/`mergedState` a `/api/sessions` row then shows. Unknown events answer `{}` and record nothing. **A hook must belong to the pane it names** (issue #181): a process that inherited a pane's `KITTERM_SESSION_ID` (a Claude Code background process) can host a conversation from another project, so when the pane already holds a join with another `session_id` and the payload's `cwd` resolves outside the pane's project (the cwd resolution of **Projects**, no label override, where two roots match when they are equal or one holds the other, so a registered root inside a checkout matches the checkout and its worktrees; for a pane with no project, a `cwd` that is not the pane's cwd or under it; the same test runs against the cwd of the terminal's foreground group leader, so `(cd other && claude)` is the pane's own while a background process is not the foreground), the pane keeps its join and its status, a `PermissionRequest` is not held, the answer is `{}` at once, and the feed gets one `agent.join-mismatch` `{sessionId, cwd, transcript}` per refused `session_id` per pane (`PtySession.admitAgentJoin`, judged in the session lookup task, off the loop; the last verdict is cached, so a repeated stranger hook costs the kernel reads of the two cwds and a `stat`). A pane with no join accepts its first hook from any `cwd`, and a payload with no `cwd` is accepted as before. **`PermissionRequest` never fires in `claude -p`** (print mode refuses instead of asking), so a non-interactive crew needs `--dangerously-skip-permissions` or `--allowedTools`, not a hold. **Full grade only**: the URL is always loopback, so this refuses nothing real, but an ungated route would let a watch caller spoof `completed`. The status lives on the `PtySession`. `kitterm hooks` prints the config (`PermissionRequest`, `PreToolUse`, `Notification`, `Stop`)

- `POST /api/sessions/<id>/input` — **write.** The request body is raw bytes typed into the shell (include your own `\n`; send `\x03` for Ctrl-C). Capped at `maxInputBytes` (64KiB → 413). Returns `{ok,bytes}`; 404 unknown session, 409 closed. **`?enter=1` presses Enter after the body as whoever reads the terminal expects it** (`PtySession.typeLine`): a shell gets the body and a `\n` in one write, exactly as before, so a submitted command is still named; a program that took the foreground gets the body in **paced pieces** (`PtySession.inputPieceBytes`: 512 bytes every 50ms, with or without `?enter=1`), a 100ms settle, then a `\r`. Claude Code's prompt keeps a bare `\n` as text and never submits, and a chunk of text with `\r` on the end is one paste whose Enter is swallowed (measured: a separate key 20ms later submits, the same write or 0ms never does). The pieces exist because Claude Code **drops every full read but the last** of a paste that arrives as fast as it reads: the kernel meters one write into 1022-byte reads on Darwin and NIO waits for the reader between them, which loses nothing (8 KiB reaches a slow raw reader whole), yet 2.1.260 kept 59 of 2104 bytes from one write and 2.1.263 kept 16 of 8193. Pieces with a pause between them arrive whole on both (measured: 512 B/100ms, 1022 B/20ms, 2044 B/100ms at 8 KiB); 512 B/50ms sits inside that with a margin, and a 64 KiB body takes about 6.5s. Time paces the pieces because nothing on the master says the reader took them: `FIONREAD`/`TIOCOUTQ` on the master count the other direction, the slave is closed after spawn, and Darwin's kqueue write filter reports zero room. A **cooked-mode** reader is a different limit, and the route refuses it (ADR 0003): a tty in canonical mode keeps `PtySession.canonicalLineBytes` of a line with no newline (1024 on Darwin, `MAX_INPUT`; 4095 on Linux) and drops the rest — measured: Darwin kept 1024 of a 2051-byte line, rang a bell per byte after and never completed the line; Linux kept 4095 of 5005 — so a body over that typed at a `sleep`, a program still starting, or a shell in a here-doc arrives cut and the daemon cannot see it. A body over the cap answers **409** `{"ok":false,"reason":"cooked","error":…,"foregroundProgram":<name or null>,"limit":<cap>,"bytes":<count>}` while `PtySession.inputIsCanonical` is true (`tcgetattr` on the master, which reports the slave's mode on both platforms), with or without `?enter=1`; **`?force=1`** types it anyway. A short body into a cooked reader still types. Who reads is `foregroundIsShell`: `tcgetpgrp` on the master, then the group leader's `argv[0]` name against the spawned shell and a known-shell set — by name, not pid, because `exec claude` keeps the shell's pid and macOS's `/bin/sh` re-executes as `bash`; no group yet or an error reads as the shell. The body may be empty with `?enter=1` (Enter alone answers a dialog). The MCP `send_input` tool uses this route for `enter:true`, its default, and folds a trailing `\n` in the text into it. That tool also takes **`keys`** — `up`, `down`, `left`, `right`, `enter`, `escape`, `ctrl-c` — and builds the body from `MCPTools.keyBytes`, because a control byte does not survive a JSON string argument on every MCP client: one that strips control characters turns the Down arrow into the two bytes `[B` (measured 2026-09-09), and one that leaves the byte raw makes the JSON-RPC line unparseable, so `MCPBridge.run` skips the whole call. A name survives both, which is what lets a foreman answer a folder-trust dialog with the toolset alone. `enter` in `keys` is this route's `?enter=1`, never a byte the bridge picked, so it can only be the last key **Off unless the daemon was started with `--agent-control`** (else 403). Input interleaves with any attached controller — no separate role
